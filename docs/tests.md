# TESTS.md — Стратегия Тестирования

Этот документ определяет границы ответственности при тестировании. Мы следуем принципу: **Крейты тестируют контракты, Пользователь тестирует сценарии.**

---

## 1. Философия Тестирования

1. **Только Юнит-Тесты:** Внутри крейтов пишутся только юнит-тесты (`#[cfg(test)] mod tests`), проверяющие базовый функционал и граничные условия отдельных функций.
2. **Отказ от Интеграции в Крейтах:** Сложные сценарии (композиция видов, многопоточные пайплайны, работа с реальным железом) **не тестируются** внутри крейтов. Это ответственность интеграционных тестов пользователя.
3. **Детерминизм:** Все тесты должны быть детерминированными и воспроизводимыми. Запрещено использовать `std::thread::sleep` или ожидание времени в юнит-тестах.
4. **`no_std` Совместимость:** Тесты должны компилироваться и работать в окружении без стандартной библиотеки (используя `core` и, при необходимости, кастомный аллокатор для тестов).

---

## 2. Расположение Тестов

Тесты размещаются непосредственно в файле модуля или в подмодуле `tests`:
```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_basic_functionality() {
        // ...
    }
}
```

## 3. Чек-листы Тестов по Крейтам

### 3.1. `raw-storage`
* **Создание:** Проверка `ArrayStorage`, `SliceStorage`.
* **Границы:** Проверка `capacity()` и корректности возврата `as_strided_view`.
* **Изменение:** Проверка записи через `StorageMut`.

### 3.2. `strided-mem`
* **Арифметика:** Проверка корректности смещений (`ptr.add`).
* **Разделение (`split`):** Проверка, что после `split_strided` сумма длин суб-видов равна исходной, а указатели не пересекаются.
* **Границы:** Проверка `get_mut` с индексом `len` (должен вернуть `None`).

### 3.3. `ring-buf`
* **Кольцевая логика:** Запись `N` элементов, проверка замыкания индекса (индекс `N` должен стать `0`).
* **Переполнение:** Проверка возврата `Err(BufferFull)` при записи в полный буфер.
* **Чтение:** Проверка порядка элементов (FIFO) после нескольких циклов записи/чтения.
* **Итераторы:** Проверка, что итератор корректно разворачивает кольцо в 2 среза (до границы и после).

### 3.4. `soa-derive` (если применимо)
* **Компиляция:** Проверка, что макрос успешно генерирует код.
* **Структура:** Проверка, что поля `x`, `y` лежат в разных массивах (через `std::ptr::addr_of!` в тестах).

## 4. Инструментарий для `unsafe` и Атомик

Так как крейт `strided-mem` содержит `unsafe`, а `spsc` использует атомики, базовых тестов недостаточно для гарантии отсутствия гонок (Data Races).

### 4.1. Использование `loom`
Для модулей, работающих с `AtomicUsize` и многопоточным доступом, **обязательно** использование крейта `loom` в юнит-тестах:
```rust
#[test]
fn test_spsc_concurrency() {
    loom::model(|| {
        // Тестирование кольцевой очереди в разных порядках выполнения потоков
    });
}
```

### 4.2. Использование `miri`
Для `strided-mem` рекомендуется запускать тесты через интерпретатор `miri` для выявления неопределенного поведения (Undefined Behavior):
```bash
cargo +nightly miri test -p strided-mem
```

## 5. Чек-лист для ИИ-агента при написании тестов
* [ ] Тест находится внутри `#[cfg(test)] mod tests`.
* [ ] Тест проверяет только одну функцию или один метод.
* [ ] Тест не создает потоков (`std::thread`), кроме случаев использования `loom::model`.
* [ ] Тест не использует файловую систему или сеть.
* [ ] Для `unsafe` кода написан тест, который вызывает панику или ошибку при неверном использовании (через `#[should_panic]`).
```
