# Структура и архитектура модулей

Этот документ описывает фундаментальные принципы проектирования, структурную иерархию компонентов и распределение ответственности внутри экосистемы библиотеки.

---

## 1. Фундаментальные Принципы (Design Principles)

Проект проектируется как высокопроизводительная (HPC), безопасная и универсальная (`no_std` first) библиотека. Архитектурный дизайн основывается на 4 столпах:

### 1.1. Высокая Связность Модуля (High Cohesion)
Каждый модуль, крейт, структура или функция выполняет **ровно одну логическую обязанность** (Single Responsibility Principle).
* Управление памятью не знает о кольцевых индексах.
* Математика смещений и виды не знают о способах аллокации.
* Кольцевой буфер не занимается распределением памяти вручную — он лишь управляет логикой очереди.
* Каждый крейт самостоятельно определяет свои типы ошибок, не вынося их в общие «мусорные» крейты.

### 1.2. Низкая Внешняя Связность (Low Coupling)
Зависимости между компонентами строго однонаправленные и ацикличные (DAG — Directed Acyclic Graph, направленный граф без циклов). Модули нижнего уровня не знают о существовании модулей верхнего уровня.
* Изменение реализаций памяти (`raw-storage`) **не должно** требовать изменений в вычислительном ядре видов (`strided-mem`).
* Замена логики кольцевых буферов **не затрагивает** механизмы расщепления срезов.

### 1.3. Строгий Контроль Unsafe (Zero-Unsafe Core Rule)
Вся работа с сырыми указателями (`*mut T`, `NonNull<T>`), арифметикой указателей и доказательством отсутствия aliasing (пересечения ссылок) **сосредоточена исключительно в крейте `strided-mem`**.
* Все остальные крейты (`raw-storage`, `ring-buf`) компилируются с флагом `#![deny(unsafe_code)]`.
* **Важно:** Используется `deny`, а не `forbid`, чтобы позволить точечное, строго задокументированное использование `unsafe` (например, для `unsafe impl Send/Sync` или интринсиков `core::hint::unreachable_unchecked`) с обязательным блоком `/// # Safety`.

### 1.4. Принцип «Память $\rightarrow$ Хранилище $\rightarrow$ Вид»
Физическая память преобразуется в структуры данных через четкое разделение ролей:
1. **Physical Memory:** Память ОС, стек, static или MMIO (Memory-Mapped I/O — ввод-вывод, отображенный на память).
2. **Storage (`raw-storage`):** Владеет байтами, управляет временем жизни (`lifetime`), обеспечивает сплошность.
3. **View (`strided-mem`):** Временно заимствует Storage. Не владеет памятью, меняет её геометрическую интерпретацию (шаги, матрицы, SoA).

## 2. Иерархия Компонентов и Чистая Архитектура

Архитектура строго подчиняется древовидной иерархии. Правило видимости и вызовов: **Сверху Вниз**.

```text
[ Уровень 4: Пользовательский API / Высшие структуры ]
                     │
                     ▼
           ┌──────────────────┐
           │     ring-buf     │  <-- 100% Safe (Кольцевые буферы, SPSC, SoA-кольца)
           └─────────┬────────┘
                     │
                     ▼
[ Уровень 3: Виды и Геометрия ]
           ┌──────────────────┐
           │   strided-mem    │  <-- Unsafe-ядро (StridedView, split, арифметика)
           └─────────┬────────┘
                     │
                     ▼
[ Уровень 2: Хранилища Памяти ]
           ┌──────────────────┐
           │   raw-storage    │  <-- Safe, no_std/alloc (Владение, &[T] / &mut [T])
           └──────────────────┘

```

## 3. Описание Крейтов и Модулей

### 3.1. `raw-storage` (Абстракция Владения Памятью)

* **Цель:** Единый абстрактный контракт физического владения/заимствования блоков памяти без географической интерпретации.
* **Атрибут:** `#![no_std]`, `#![deny(unsafe_code)]`
* **Ключевой контракт:** Трейты `Storage` и `StorageMut` предоставляют доступ к емкости (`capacity()`) и сплошным срезам `&[T]` / `&mut [T]`. Крейт ничего не знает о `strided-mem` или шагах (stride).
* **Ключевые модули и типы:**
* `traits`:
* `Storage` — базовый контракт чтения (`fn as_slice(&self) -> &[T]`).
* `StorageMut` — контракт записи (`fn as_mut_slice(&mut self) -> &mut [T]`).
* `ResizableStorage` — контракт для растущей памяти (требует feature `alloc`).


* `impls`:
* `ArrayStorage<T, N>` — хранилище на базе статического массива (для Embedded).
* `SliceStorage<'a, T>` — хранилище, заимствующее внешний срез.
* `AllocStorage<T>` — динамическое хранилище на базе `Vec<T>`.


* `error`: Собственный тип `StorageError`, реализующий трейт `core::error::Error`.



### 3.2. `strided-mem` (Геометрия, Виды и Unsafe-Ядро)

* **Цель:** Изолированная арифметика указателей, построение видов над `raw-storage`, непересекающиеся sub-виды, многомерные шаги.
* **Атрибут:** `#![no_std]` (**Единственное место с глобальным разрешением `unsafe**`)
* **Ключевой контракт:** Конструирует первичный `StridedViewMut` (со `stride = 1`) поверх любого типа, реализующего `StorageMut`, и предоставляет API для построения иерархии «Видов над Видами» без блокировок.
* **Ключевые модули и типы:**
* `pointer`: Безопасные обертки вокруг `NonNull<T>`.
* `views`: `StridedView<'a, T>`, `StridedViewMut<'a, T>`.
* `split`: Метод `split_strided` на `StridedViewMut` для разделения вида на $N$ непересекающихся мутабельных суб-видов.
* `error`: Собственный тип `StridedError` (например, `OverlapDetected`, `ZeroStride`).


* **Тестирование:** Обязательное использование крейта `loom` для детерминированного тестирования многопоточных инвариантов и гонок (Data Races).

### 3.3. `ring-buf` (Высшая Логика Кольцевых Буферов)

* **Цель:** Предоставление пользователю высокоуровневых структур кольцевых буферов.
* **Атрибут:** `#![no_std]`, `#![deny(unsafe_code)]`
* **Ключевые модули и типы:**
* `ring`: `RingBuffer<S: Storage>` — базовый владеющий кольцевой буфер.
* `view`: `RingBufferView<'a, T>` — заимствующий кольцевой буфер (может быть построен поверх `StridedViewMut`).
* `spsc`: `SpscRingBuffer` — lock-free очередь (использует `AtomicUsize` с `Acquire/Release`).
* `soa`: `SoARingBuffer` — кольцевой буфер для Structure of Arrays.
* `iter`: SIMD-friendly итераторы, разворачивающие кольцо в 1 или 2 непрерывных среза.
* `error`: Собственный тип `RingBufferError` (например, `BufferFull`, `BufferEmpty`).



### 3.4. `soa-derive` (Proc-Macro Крейт)

* **Цель:** Генерация SoA-адаптеров для пользовательских структур.
* **Тип:** `proc-macro = true`
* **Функция:** Позволяет написать `#[derive(SoA)]` над обычной структурой и автоматически сгенерировать параллельные хранилища и итераторы.

## 4. Внешние Зависимости и Обработка Ошибок

Проект стремится к **Zero External Dependencies** (нулю внешних зависимостей в релизе). Единственное исключение — крейт `loom` для тестирования многопоточности.

* **Система ошибок:** Каждый крейт реализует собственный тип ошибки вручную (без использования сторонних derive-макросов), реализующий стандартный трейт `core::error::Error`.
* **Детали:** Полное описание архитектуры ошибок, стратегия условной компиляции и оптимизация размера типов вынесены в отдельный документ **`errors.md`**.
