# ARCHITECTURE.md: Манифест архитектуры библиотеки кольцевых буферов и математических вычислений на Rust

## 1. Введение и цели проекта

Настоящий документ определяет ключевые архитектурные принципы, ограничения и шаблоны проектирования при миграции и переосмыслении существующей библиотеки C-кольцевых буферов на язык Rust.

### Главные цели (Goals):

1. **Zero-Cost Abstractions (Отсутствие платы за абстракции):**
Все высокоуровневые удобства API (виды, SoA-прокси, стРАЙД-деление, кастомная индексация) должны компилироваться в эквивалентный или более оптимальный ассемблерный код, чем исходный C-код, без скрытых динамических аллокаций, виртуальных таблиц (`dyn Trait`) и накладных расходов в рантайме.
2. **Platform & Environment Independence (`no_std` First):**
Библиотека должна быть на 100% независима от наличия операционной системы и динамического аллокатора кучи. Код должен одинаково эффективно выполняться как на bare-metal микроконтроллерах (STM32, ESP32, RISC-V), так и на серверных платформах (Linux, Windows, macOS) и в высокопроизводительных вычислениях (HPC — High-Performance Computing). Программист должен иметь свободу в собственной реализации низкоуровневой работы с памятью. Все структуры абстрагированы от конкретного низкоуровневого хранилища.
3. **Data-Race Free Parallelism & Compile-Time Safety (Безопасность):**
Гарантия отсутствия Data Races (состояний гонки) и UB (Undefined Behavior — неопределенного поведения). Любые сложные операции деления памяти должны проверяться на этапе компиляции или быть защищены безопасными низкоуровневыми примитивами.
4. **Ergonomics & Developer Experience (Удобство использования):**
API должен быть интуитивным, использовать идиоматичный Rust (метод-чейнинг, итераторы, безопасный доступ через структуру-прокси `p.x` для SoA) и сводить к минимуму необходимость написания бойлерплейта при манипуляции математическими представлениями данных.
5. **HPC & SIMD Readyness (Высокопроизводительные вычисления):**
SIMD (Single Instruction, Multiple Data — выполнение одной инструкции над множеством данных одновременно). Память должна быть организована так, чтобы обеспечивать максимальную локальность данных в L1/L2 кэше процессора, поддерживать автовекторизацию компилятора и быть совместимой с вычислениями в параллельных потоках (например, через библиотеку Rayon).

## 2. Ключевые архитектурные принципы

### Принцип 1. Разделение Хранилища (Storage) и Представлений (Views)

В отличие от подходов C++ (где аллокатор зашит в шаблон типа), в Rust библиотека строго разделяет концепцию **Владельца данных** и **Вида на данные**:

* **Storage (`S`):** Отвечает за владение памятью. Не имеет значения, чем является `S` — статическим массивом `[T; N]`, куском стека или `Vec<T>`. Требуется лишь способность предоставлять срез данных через стандартный трейт `AsMut<[T]>` / `AsRef<[T]>`.
* **View (Представление):** Не владеет памятью. Работает поверх ссылок с временем жизни (`&'a mut`) или указателей `NonNull<T>`. Вид полностью абстрагирован от того, как и где была выделена память.

### Принцип 2. Локализация `unsafe` в низкоуровневых примитивах (Sound Boundaries)

Код библиотеки делится на три слоя:

1. **Low-Level Unsafe Primitives (`StridedSliceMut<'a, T>`):**
Узкий, жестко протестированный слой, работающий с сырыми указателями (`NonNull<T>`) и шагами памяти (stride). Это **единственное место**, где разрешен `unsafe`.
2. **Compile-Time Safety Layers (`SplitStrided` Trait):**
Слой, проверяющий математические инварианты непересечения срезов на этапе компиляции с использованием Const Generics (констант времени компиляции).
3. **High-Level Safe API (`RingBuffer`, `SoARingBuffer`, `StridedRingBuffer`):**
Высшие структуры данных. **Внутри них не должно быть ни одного слова `unsafe`!** Они строятся поверх безопасных низкоуровневых видов и полагаются на проверку заимствований (Borrow Checker) самого Rust.

## 3. Архитектурная структура и компоненты

```text
               +-------------------------------------------+
               |  Memory Storage (Static / Stack / Heap)   |
               +-------------------------------------------+
                                     |
                                     v
               +-------------------------------------------+
               |   Owning RingBuffer<T, S> (#![no_std])     |
               +-------------------------------------------+
                                     |
                         .split_strided::<N>()
                                     |
                  +------------------+------------------+
                  |                                     |
                  v                                     v
   +------------------------------+      +------------------------------+
   | StridedRingBuffer<'a, T> [0] |      | StridedRingBuffer<'a, T> [1] |
   |  (e.g., Чётные элементы)     |      |  (e.g., Нечётные элементы)   |
   +------------------------------+      +------------------------------+
                  |                                     |
                  +------------------+------------------+
                                     |
                                     v (Parallel Threads / SIMD)
```

### 3.1. Модель памяти и `no_std` совместимость

В начале корня библиотеки (`src/lib.rs`) **обязательно** указывается атрибут:

```rust
#![no_std]
```

Если требуется поддержка динамической памяти для `std`/`alloc` сред, это включается исключительно через опциональный feature-flag в `Cargo.toml`:

```toml
[features]
default = []
alloc = []
std = ["alloc"]
```

### 3.2. Базовый низкоуровневый примитив: Strided-срез

Все сложные операции разделения кольцевых буферов опираются на внутреннюю структуру `StridedSliceMut<'a, T>`, описывающую элементы в памяти, расположенные с постоянным шагом `stride`.

```rust
use core::marker::PhantomData;
use core::ptr::NonNull;

/// Мутабельный вид на элементы с постоянным шагом (stride).
/// Является базовым строительным блоком для разнесения данных.
pub struct StridedSliceMut<'a, T> {
    ptr: NonNull<T>,
    stride: usize,
    len: usize,
    _marker: PhantomData<&'a mut T>,
}

impl<'a, T> StridedSliceMut<'a, T> {
    /// # Safety
    /// Вызывающий код обязан гарантировать, что диапазон памяти
    /// `[ptr + i * stride]` не перекрывается ни с какими другими активными ссылками.
    pub unsafe fn new_unchecked(ptr: NonNull<T>, stride: usize, len: usize) -> Self {
        Self { ptr, stride, len, _marker: PhantomData }
    }

    #[inline(always)]
    pub fn len(&self) -> usize {
        self.len
    }

    #[inline(always)]
    pub fn get_mut(&mut self, index: usize) -> Option<&mut T> {
        if index >= self.len {
            return None;
        }
        unsafe {
            let elem_ptr = self.ptr.as_ptr().add(index * self.stride);
            Some(&mut *elem_ptr)
        }
    }
}

// Гарантируем возможность безопасной передачи вида между потоками (HPC / Multithreading)
unsafe impl<'a, T: Send> Send for StridedSliceMut<'a, T> {}
unsafe impl<'a, T: Sync> Sync for StridedSliceMut<'a, T> {}
```

> **Правило оптимизации кольцевой индексации (Ring Indexing Rule):**
> 1. Ёмкость кольцевого буфера (`Capacity`) **всегда** должна быть степенью двойки (\(2^n\)).
> 2. Запрещено использовать оператор `%` (modulo) для вычисления физического индекса, так как он блокирует автовекторизацию (SIMD).
> 3. Вместо `% Capacity` необходимо использовать битовое И: `index & (Capacity - 1)`.

### 3.3. Разделение буферов на этапе компиляции (Compile-Time Split)

Разделение кольцевого буфера на \(N\) независимых подбуферов (например, чередующиеся элементы для параллельной обработки) реализуется через Трейты с использование `Const Generics`:

```rust
pub trait SplitStrided<'a, T> {
    fn split_strided<const STRIDE: usize>(self) -> [StridedSliceMut<'a, T>; STRIDE];
}

impl<'a, T> SplitStrided<'a, T> for &'a mut [T] {
    fn split_strided<const STRIDE: usize>(self) -> [StridedSliceMut<'a, T>; STRIDE] {
        // Современный идиоматичный способ проверки на этапе компиляции
        const { assert!(STRIDE > 0, "Stride must be greater than zero") };

        let len = self.len();
        let base_ptr = NonNull::new(self.as_mut_ptr()).expect("Null buffer pointer");

        core::array::from_fn(|offset| {
            let sub_len = if len > offset {
                (len - offset + STRIDE - 1) / STRIDE
            } else {
                0
            };

            unsafe {
                let start_ptr = NonNull::new_unchecked(base_ptr.as_ptr().add(offset));
                StridedSliceMut::new_unchecked(start_ptr, STRIDE, sub_len)
            }
        })
    }
}
```

### 3.4. Абстракция SoA (Structure of Arrays) и Ref-структуры

При миграции C-кода с SoA-структурами (для SIMD и кэш-эффективности) запрещается использовать единые массивы C-структур (AoS — Array of Structures). SoA-кольцевой буфер должен предоставлять возможность обращения к элементам через временные **Proxy / Ref-структуры**.

Паттерн реализации SoA Ref:

```rust
// Временный прокси-вид на элемент SoA в кольцевом буфере
pub struct ParticleRefMut<'a> {
    pub x: &'a mut f32,
    pub y: &'a mut f32,
    pub z: &'a mut f32,
}

// SoA хранилище
pub struct ParticleSoAStorage<const N: usize> {
    pub x: [f32; N],
    pub y: [f32; N],
    pub z: [f32; N],
}
```

> **Паттерн итераторов для SoA:**
> Для итерации по SoA-буферах агент обязан реализовать кастомные структуры-итераторы (например, `SoAIterMut<'a>`), которые на каждом шаге (`next()`) конструируют и возвращают `ParticleRefMut<'a>`. Это сохраняет Zero-Cost абстракцию и позволяет использовать `for`-циклы и параллельные итераторы без аллокаций.

### 3.5. Модель параллелизма и обработка ошибок

> **Модель параллелизма (Concurrency Model):**
> Базовая реализация кольцевого буфера использует модель SPSC (Single Producer, Single Consumer — одиночный производитель, одиночный потребитель).
> * Индексы `head` (запись) и `tail` (чтение) должны храниться в типе `core::sync::atomic::AtomicUsize`.
> * При чтении и записи индексов **обязательно** использовать семантику упорядочивания памяти (Memory Ordering): `Ordering::Release` при обновлении индекса и `Ordering::Acquire` при его чтении. Это гарантирует видимость данных в кэше других ядер процессора без использования тяжелых мьютексов (`Mutex`).
>
> **Обработка ошибок (Error Handling):**
> В режиме `no_std` библиотека должна предоставлять собственный легковесный `enum RingBufferError { Full, Empty, OutOfBounds }`. Методы, которые могут завершиться ошибкой (например, `push` в полный буфер), должны возвращать `Result<(), RingBufferError>`, а не паниковать (`panic!`), за исключением случаев нарушения инвариантов безопасности (Safety Invariants).

## 4. Инструкция для ИИ-агента по проведению рефакторинга / миграции

При переносе конкретных функций и C-файлов на Rust, ИИ-агент обязан следовать алгоритму:

1. **Анализ C-кода:**
* Определить: функция владеет памятью, изменяет её по месту или просто читает?
* Выделить математическое ядро алгоритма отдельно от индексации ring-буфера.

2. **Выбор абстракции:**
* Если функция производит векторизованные вычисления — принимать срезы `&[T]` / `&mut [T]` или `StridedSliceMut<'a, T>`.
* Если функция управляет состоянием кольца — оборачивать вычисления в методы высших RingBuffer-структур.

3. **Проверка Zero-Cost:**
* Все методы доступа (`get_mut`, `index`) должны помечаться атрибутом `#[inline(always)]`.
* Избегать системных вызовов, проверок границ (bounds checks) там, где компилятор может выдать векторный код, либо использовать безопасные итераторы вместо явной индексации `for i in 0..N`.

4. **Обеспечение безопасности (Safety Rules):**
* Запрещено использовать `unsafe` блок, если задачу можно решить через безопасное деление срезов (`split_at_mut`, `chunks_exact_mut`) или вышеописанный `split_strided`.
* Каждая функция, использующая `unsafe`, должна иметь подробную документацию в секции `/// # Safety` с математическим доказательством отсутствия выгрузки за границы памяти.

### 4.1. Алгоритм миграции функции из C в Rust (Step-by-Step)

1. **Анализ памяти:** Является ли функция чисто математической (работает со срезами `&[T]`) или она управляет состоянием кольца (`head`/`tail`)?
2. **Выбор примитива:**
   * Для линейных математических ядер используй `&mut [T]` или `StridedSliceMut`.
   * Для управления очередью используй `RingBufferView` с `AtomicUsize`.
3. **Инвариант ёмкости:** Если функция использует кольцевую индексацию, замени `% Capacity` на `& (Capacity - 1)`. Убедись, что `Capacity` всегда степень двойки.
4. **Граница `unsafe`:** Помни, что `unsafe` разрешен ТОЛЬКО внутри `StridedSliceMut::new_unchecked` и `split_at_offsets`. Любая математика индексов в вышестоящих структурах (`RingBuffer`, `SoA`) должна быть на 100% безопасной (Safe Rust) и использовать `debug_assert!` для проверки границ.
5. **Отсутствие скрытых аллокаций:** Запрещено использовать `Vec`, `String`, `Box` или `.collect::<Vec<_>>()`. Все итераторы и коллекции должны быть ленивыми (Lazy) или опираться на стековую память (`[T; N]`) и внешние аллокаторы.

## 5. Чек-лист готовности модуля (Definition of Done)

Модуль считается успешно мигрированным на Rust, если:

* [ ] Код компилируется с флагом `#![no_std]` без ошибок.
* [ ] Никакой метод не требует наличия динамической кучи (`alloc` / `malloc`).
* [ ] Все операции деления буферов на непересекающиеся виды (`Strided`) гарантируют отсутствие Data Race на уровне системы типов (компилятором).
* [ ] Написаны unit-тесты, проверяющие корректность работы закольцованной индексации (границы tail/head) с использованием битового маскирования.
* [ ] Отсутствуют неблокируемые предупреждения компилятора (`cargo check` выводит 0 warnings).
* [ ] Индексы `head` и `tail` реализованы через атомарные примитивы с корректным Memory Ordering.
