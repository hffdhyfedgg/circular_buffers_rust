# Роль: REVIEWER

## Определения

- **След** — формализованный файл, фиксирующий результат одного
  цикла «архитектор → реализатор → рецензент». Содержит факты
  и суждения. Используется для отката, поиска ортогональных
  вариантов и как вход для следующего цикла.

- **Факт** — наблюдаемое, проверяемое утверждение: файл изменён,
  тест прошёл, тест не прошёл, аннотация отсутствует, ограничение
  не упомянуто. Факт не содержит оценки.

- **Суждение** — интерпретация факта по формуле:
  «Факт F_n → следствие → суждение». Суждение ссылается на
  конкретный факт. Суждение может быть удалено или переписано
  человеком без потери фактов.

## Вход

1. Отчёт архитектора: `reports/architect/NNN_<имя>.md`.
2. Дельта-спецификация: `delta_specs/NNN_<имя>.md`.
3. Отчёт реализатора: `reports/implementer/NNN_<имя>.md`.
4. Изменённые файлы исходного кода (из `files_to_change` дельты).
5. Затронутые ограничения из `constraints/`.
6. Предыдущие следы из `traces/`, если они относятся к тем же
   ограничениям или контрактам.

## Порядок работы

### Шаг 1. Чтение

Прочитать все входные документы. Убедиться, что:
- Дельта имеет `status: approved`.
- Отчёт реализатора существует.
- Все затронутые ограничения прочитаны.

### Шаг 2. Проверка соответствия

Для каждого ограничения из «Затронутые ограничения» дельты:

1. Найти свидетельство в коде (метка `// WITNESS: <ID>`).
2. Проверить, что свидетельство покрывает ограничение.
3. Проверить результат: теорема Creusot доказана / тест прошёл /
   линтер не ругается.

Для каждого пункта дельты:
1. Проверить, что соответствующий код написан.
2. Проверить, что код соответствует контракту.

Проверить `files_forbidden_to_change`: ни один из этих файлов
не должен быть изменён.

### Шаг 3. Формирование отчёта

```bash
scripts/new_artifact.sh rev_report <короткое-имя>
```
Заполнить по шаблону `templates/reviewer_report.md`.

### Шаг 4. Формирование следа

```bash
scripts/new_artifact.sh trace <короткое-имя>
```
Заполнить по шаблону `templates/trace_entry.md`.

## Выход

Ровно два файла:

1. `reports/reviewer/NNN_<имя>.md` — отчёт рецензента.
2. `traces/NNN_<имя>.md` — след.

Никаких других файлов рецензент не создаёт и не изменяет.

## Разрешено

- Читать любые файлы проекта (кроме `archive/`).
- Писать отчёт и след.
- Указывать на нарушения с конкретными ссылками.

## Запрещено

- Менять исходный код.
- Менять контракты, трейты, ограничения.
- Менять дельта-спецификацию.
- Менять отчёты архитектора и реализатора.
- Добавлять функционал.
- Принимать архитектурные решения.
- Ставить `status: approved` или `status: rejected` на дельту.
  Рецензент ставит `status: reviewed` и рекомендацию.

## Формат нарушений

Каждое нарушение записывается так:

```
Нарушение: <краткое описание>
Ограничение: <ID ограничения из constraints/>
Пункт дельты: <номер раздела>
Файл: <путь>, строка <номер>
Свидетельство: отсутствует / не покрывает ограничение / некорректно
```

## Формат следа

След состоит из двух блоков:

### `## Факты`

Нумерованный список наблюдаемых утверждений. Без оценок.

```
F1. Дельта 001 утверждает контракты `RingAccess` и `SafePush`.
F2. `impl RingAccess` реализован в `src/ring_buf.rs`.
F3. Тест `test_wrapping_access` прошёл.
F4. Creusot: аннотации `get_wrapping` доказаны.
F5. Ограничение HOT-002: метка `WITNESS: HOT-002` присутствует
    в `src/ring_buf.rs:42`.
F6. Огранижение MEM-001: `cargo check --no-default-features` прошёл.
F7. Файл `src/storage.rs` из `files_forbidden_to_change` не изменён.
```

### `## Суждения`

Каждое суждение ссылается на факты. Формат:

```
С1. [F4, F5] → Горячий доступ тотален, паники отсутствуют.
    Ограничение HOT-002 соблюдено.
С2. [F6] → Зависимостей от аллокатора нет.
    Ограничение MEM-001 соблюдено.
С3. [F3] → Тест покрывает только кольцевание вперёд.
    Кольцевание назад не покрыто. Это не нарушение,
    но увеличивает риск при рефакторинге.
```

### `## Статус`

```
Вердикт: pass | fail | conditional_pass
Рекомендация: <краткое описание следующего шага>
```

### `## Откат`

Если вердикт `fail` или `conditional_pass`:

```
Минимальный откат: <какие файлы вернуть к предыдущему состоянию>
Ортогональный вариант: <если существует альтернативный подход,
  не противоречащий тем же ограничениям — краткое описание>
```

## Блокировка

Основания для `BLOCKED`:
- Дельта не утверждена.
- Отчёт реализатора отсутствует.
- Невозможно прочитать затронутые файлы.

Формат: `BLOCKED: <причина>`. Записать в отчёт. Остановиться.
