Ниже — минимально рабочий, но уже жёсткий SDD-контур. Я намеренно не раздуваю его полной бюрократией. Оставим только то, что реально защищает от слабых агентов, хаоса и “попробовал всё сразу”.

Главный принцип процесса:

```text
Сначала архитектура.
Потом дельта-спецификация.
Потом кодогенерация.
Потом отчёт.
```

И отдельно важный момент:

```text
Архитектор не пишет реализацию.
Реализатор не принимает архитектурных решений.
Если реализатору нужно принять решение — он останавливается.
```

Это защищает от хрупкости лучше, чем любые тяжёлые обвязки.

# 2. Краткая схема процесса

Для каждой задачи агент работает так:

```text
1. Задача попадает в STATE.md.
2. Агент-архитектор читает ограничения и пишет дельта-спецификацию.
3. Человек утверждает дельта-спецификацию.
4. Агент-реализатор пишет код строго по дельта-спецификации.
5. Агент делает проверку и создаёт отчёт.
6. Человек принимает отчёт.
```

Запрещено смешивать роли:

```text
ARCHITECT mode:
- думает;
- фиксирует контракты;
- пишет дельта-спецификацию;
- не пишет реализации.

IMPLEMENTER mode:
- читает только утверждённую дельта-спецификацию;
- пишет код;
- не меняет архитектуру;
- не задаёт новые архитектурные вопросы.

REVIEWER mode:
- проверяет соответствие ограничениям;
- не добавляет фичи.
```

## Безопасность

### `SAF-001`

```yaml
id: SAF-001
title: Безопасность доказуется на этапе компиляции, а не в конструкторе
status: active
hard: true
layer: safety

rule: >
  Конструкторы горячих типов не должны выполнять рантайм-доказательства
  безопасности памяти.

  Безопасность должна следовать из:
    - системы типов;
    - времён жизни;
    - константных параметров;
    - статически проверяемых инвариантов;
    - документированных unsafe-инвариантов, подтверждённых офлайн-верификацией.

  Допустимые механизмы:
    - borrow checker
    - lifetimes
    - typestate
    - const generics
    - const assertions
    - total-by-construction API
    - unsafe with offline proof obligations

  Запрещено:
    - полагаться на рантайм-проверки как на доказательство безопасности
      в горячих путях
    - делать проверки в конструкторе, если они являются единственным
      источником безопасности

  Холодные проверяемые конструкторы допускаются,
  но они не создают права для горячего безопасного доступа,
  если безопасность не доказана статически.

enforcement:
  - architecture delta spec
  - code review
  - Kani/test witnesses offline
```

### `SAF-002`

```yaml
id: SAF-002
title: Мутабельные разделения только при доказанном непересечении
status: active
hard: true
layer: safety

rule: >
  Из одной области памяти можно создавать несколько мутабельных
  представлений только если их непересечение доказано.

  Доказательство должно быть:
    - статическим;
    - структурным;

    - чётные/нечётные элементы через страйд 2
    - непересекающиеся страйд-классы
    - индексные множества с доказанной уникальностью,
      если уникальность установлена статически или через явный контракт

enforcement:
  - architecture delta spec
  - Kani/test witnesses
  - code review
```

## Горячие пути

### `HOT-001`

```yaml
id: HOT-001
title: Горячие API без Option и Result
status: active
hard: true
layer: hot-path

rule: >
  Горячие операции не должны возвращать Option или Result.

  Горячие операции должны быть:
    - тотальными по построению;
    - или явно небезопасными с документированными предусловиями.

  Примеры горячих операций:
    - доступ по кольцевому индексу
    - push с перезаписью
    - итерация по горячему буферу
    - свёртки
    - математические ядра
    - доступы в представлениях, где границы доказаны

  Если операция может завершиться ошибкой по причине,
  которую нельзя устранить статически,
  она не является безопасной горячей операцией.

required_naming:
  hot_total:
    - get_wrapping
    - push_overwrite
    - next_wrapping
  hot_unchecked:
    - get_unchecked
    - push_unchecked
  cold_checked:
    - get
    - try_push
    - try_resize

enforcement:
  - architecture delta spec
  - code review
```

  - tests
  - architecture delta spec

## Кольцевые буферы

### `RING-001`

```yaml
id: RING-001
title: Горячая кольцевая индексация тотальна
status: active
hard: true
layer: ring-buf

rule: >
  Горячий доступ к кольцевому буферу должен быть тотальным
  за счёт кольцевания.

  Если буфер моделируется как всегда заполненный кольцевой массив,
  доступ по относительному индексу должен возвращать элемент
  без Option и без Result.

  Если буфер может быть пустым,
  горячий безопасный доступ без элемента невозможен.
  В этом случае нужно:
    - использовать холодный проверяемый доступ;
    - или использовать тип, который гарантирует непустоту;
    - или использовать небезопасный доступ с предусловием
      "буфер не пуст".

  Запрещено:
    - возвращать Option в горячем кольцевом доступе
    - паниковать в горячем кольцевом доступе
    - молча смешивать очередь и всегда полный кольцевой массив
      в одном горячем контракте

enforcement:
  - architecture delta spec
  - code review
```

    - Kani-пруфы
    - примеры использования
    - статические тесты

    - холодный проверяемый путь;
    - отладочный механизм;
    - диагностический контракт.

  Они не являются доказательством безопасности горячего пути.

enforcement:
  - tests
  - cargo kani
  - report evidence

# 7. `spec/20_process.md`

Это описание самого процесса работы.

```markdown
# Process

## Общий принцип

Работа ведётся по фазам.

Запрещено переходить к следующей фазе,
если предыдущая не завершена и не утверждена.

---

## Фазы задачи

### Фаза 0. Постановка

Человек фиксирует задачу в `STATE.md`.

Задача должна быть сформулирована как изменение проекта,
а не как свободное исследование.

Пример:

```text
Разделить горячие и холодные контракты в представлениях памяти.
```

Плохой пример:

```text
Сделай красиво и безопасно.
```

---

### Фаза 1. Архитектурный проход

Запускается агент в роли `ARCHITECT`.

Вход:

```text
STATE.md
AGENTS.md
spec/00_charter.md
spec/10_constraints.md
spec/20_process.md
исходный код, если нужен для анализа
```

Выход:

```text
черновик дельта-спецификации
```

На этой фазе запрещено:

- писать реализации;
- менять код;
- добавлять тесты под новую архитектуру;
- менять ограничения.

Разрешено:

- анализировать;
- предлагать контракты;
- выявлять конфликты;
- писать дельта-спецификацию.

---

### Фаза 2. Утверждение человеком

Человек читает дельта-спецификацию.

Человек имеет право:

- утвердить;
- отклонить;
- отправить на доработку;
- задать вопросы;
- выбрать один из предложенных вариантов.

Утверждение фиксируется в самой дельта-спецификации:

```yaml
status: approved
```

Без этого поля реализация запрещена.

---

### Фаза 3. Контрактный проход, если нужен

Если дельта-спецификация требует новых трейтов,
сначала могут быть созданы только трейты и контрактные сигнатуры.

Это отдельный подэтап:

```text
contract skeleton pass
```

На нём разрешено:

- добавлять трейты;
- добавлять сигнатуры;
- добавлять документацию контрактов;
- добавлять пустые реализации только если они нужны для компиляции.

Запрещено:

- писать полноценную реализацию;
- менять логику существующих модулей;
- добавлять горячие алгоритмы.

---

### Фаза 4. Реализация

Запускается агент в роли `IMPLEMENTER`.

Вход:

```text
утверждённая дельта-спецификация
```

Выход:

```text
код
тесты
отчёт
```

Реализатор обязан:

1. Читать только утверждённую дельта-спецификацию.
2. Менять только файлы из списка `files_to_change`.
3. Не принимать архитектурных решений.
4. При любой неоднозначности останавливаться.

Если реализатор считает, что дельта-спецификацию нужно изменить,
он пишет:

```text
BLOCKED: требуется изменение дельта-спецификации
```

и не продолжает.

---

### Фаза 5. Проверка

Минимальный набор проверок:

```bash
cargo fmt --check
cargo check --workspace --no-default-features
cargo check --workspace --features alloc
cargo test --workspace --no-default-features
```

Если изменение затрагивает безопасность,
запускается Kani для затронутых крейтов:

```bash
cargo kani -p <crate>
```

Если проверка не проходит, задача не считается выполненной.

---

### Фаза 6. Отчёт

Агент создаёт отчёт в `reports/`.

Отчёт обязан содержать:

```text
что сделано
по какой дельта-спецификации
какие ограничения затронуты
какие проверки пройдены
какие обязательства остались открытыми
```

Если задача не завершена, отчёт должен иметь статус:

```yaml
status: blocked
```

или

```yaml
status: failed
```

## Правила атомарности

Одна задача должна быть атомарной.

Атомарность означает:

```text
одна дельта-спецификация
один архитектурный срез
один набор файлов
одна цель
```

Запрещено:

- смешивать рефакторинг и новую функциональность;
- менять три крейта, если в дельта-спецификации указан один;
- исправлять соседние ошибки без отдельного пункта;
- “заодно” переименовывать модули;
- “заодно” менять публичные контракты.

Если обнаружена соседняя проблема:

1. Она не исправляется немедленно.
2. Она записывается в `STATE.md` как новая задача.

## Как избежать хрупкости слабых агентов

Для слабых агентов вводятся явные предохранители.

### 1. Запрет на широкую задачу

Агент не получает задачу вида:

```text
починить весь проект
```

Он получает только:

```text
реализовать дельта-спецификацию такую-то
```

---

### 2. Белый список файлов

В дельта-спецификации всегда указываются:

```yaml
files_to_change:
  - ...
files_forbidden_to_change:
  - ...
```

Агент не имеет права менять другие файлы.

---

### 3. Запрет на вопросы во время кодогенерации

Если реализатор хочет спросить:

```text
а как лучше?
```

он обязан остановиться.

Вопросы допускаются только до утверждения дельта-спецификации.

---

### 4. Раздельные запуски

Рекомендуется вручную запускать агента двумя отдельными командами.

#### Запуск архитектора

```text
Прочитай:
  AGENTS.md
  STATE.md
  spec/00_charter.md
  spec/10_constraints.md
  spec/20_process.md

Твоя роль: ARCHITECT.

Задача:
  <описание задачи>

Создай черновик дельта-спецификации.
Не изменяй исходный код.
Не принимай финальных решений без утверждения.
```

#### Запуск реализатора

```text

  AGENTS.md
  STATE.md
  spec/10_constraints.md
  spec/20_process.md

Твоя роль: IMPLEMENTER.

Ты можешь изменять только файлы, указанные в дельта-спецификации.
Если тебе нужно принять архитектурное решение — остановись.
```

# 11. Важное замечание по компиляции и конструкторам

Нужно быть честным: в Rust невозможно статически доказать вообще всё, что зависит от рантайм-значений. Поэтому в ограничениях и введена следующая модель:

```text
Если свойство доказуемо статически:
  делаем безопасный горячий путь.

Если свойство недоказуемо статически:
  либо холодный безопасный путь,
  либо горячий небезопасный путь,
  либо тотальный путь с другим инвариантом.
```

То есть мы не пытаемся сделать невозможное. Мы явно разделяем:

```text
hot-total       — безопасно и тотально по построению
hot-unchecked   — горячо, но ответственность на контракте
cold-checked    — безопасно, но с проверками
setup           — этап подготовки, не горячий
```

Это прямо закрывает ваш конфликт между:

```text
безопасность
горячие пути без Option/Result
отсутствие паник
динамические данные из C
```

# 12. Что я бы сделал самой первой дельта-спецификацией

Я бы начал не с кольцевых буферов, а с более раннего слоя.

Первая дельта-спецификация должна быть примерно такой:

```text
Название:
  Разделение контрактов на горячие и холодные,
  фиксация требований к представлениям памяти.

Цель:
  Зафиксировать, какие методы в сырых хранилищах и представлениях
  являются горячими, какие холодными,
  и какие инварианты должны доказываться статически.

Запрещено:
  менять реализации кольцевых буферов.

Разрешено:
  создать/уточнить трейты:
    Storage
    StorageMut
    RawExtent
    View
    ViewMut
    Contiguous
    Ringed
```

Это позволит сначала зафиксировать контрактную геометрию,
а уже потом трогать `CBuf`, `RingView`, `FilterBank` и остальное.

```text

```

то есть уже не шаблон, а конкретный архитектурный документ для первого прохода.
